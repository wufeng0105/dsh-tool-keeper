# Tool Keeper

**MCP 给你的工具，你可以挑、可以改。**

---

## 你大概遇到过这件事

配好一个 MCP 服务器，它很高兴地告诉你：我这儿有 14 个工具。

你常用的那两个是搜索和读正文。剩下十二个是建数据集、给钱包充值、取消监控任务、列出已有数据集……你一年也用不上一次。

但这还不是最烦的。最烦的是：

> **它们叫什么、怎么介绍自己，你一个字都改不了。**

说明是服务器厂商写的。它写的是它想让你知道的——比如：

> "You MUST call this function before 'Query Documentation' tool to obtain a valid
> Context7-compatible library ID UNLESS the user explicitly provides a library ID
> in the format '/org/project'..."

两百多个字符，全是大写命令句，在跟你的模型说「你必须先调用我」。

**你的模型读到的就是这些话。** 你说不上话。

---

## 所以麻烦在哪

**一、模型会挑花眼**

工具箱里摆着 40 多个工具、名字还都很像的时候，模型是有可能拿错工具的。
`web_search_exa` 和 `mcp__tinyfish__search` 都是搜网页，它挑哪个？说明写得越啰嗦，判断越容易被带偏。

你希望它用的那个，往往不是名字最长、说明最花哨的那个。

**二、说明里的话不是你写的**

厂商的说明里经常带着「必须先用我」「不要用那个」这类指令。
这些话会跟你的真实需求打架。你想让它直接读网页，它却先去解析了个库 ID。

**三、占地方**

这条最不重要，但顺带说一句：模型每答一句话，都要把全部工具的说明重读一遍（它没有记忆，每轮都是重新收到一整套）。
工具多、说明长，每轮就重得多。**这一条是前两条的副产品，不是主要理由。**

---

## 这个插件做两件事

**一、让用不上的工具彻底消失**

不是界面上藏起来。是真的不发给模型——它从工具清单里消失，模型根本不知道有这个东西存在。

**二、改说明**

把厂商那段两百字的命令句，改成你自己的一句话。

> 第二件是这个插件真正特别的地方。DSH 自带的 `restrict()` 只能把工具拿掉，
> **改不了工具说的话**。为了拿到「能改」这个能力，这个插件绕了不少路
> （详见 [docs/DESIGN.md](./docs/DESIGN.md) 第一节）。

---

## 装上之后

**什么都不做也是对的。出厂状态不管任何工具**——工具数量、说明文字，跟没装这个插件完全一样。

为什么这样设计？因为「哪个该关、哪句话该改」只有你知道。
一个管理工具如果出厂就替你决定关掉什么，那是替你砍功能。

### 先看看现在是什么样

跟模型说一句：

> 列出所有工具

它会按来源分组报给你，每个工具带字符数。你会看到一个真实的对比，比如：

```
内置工具                    49 个
MCP · tinyfish              43 个   ← 你常用的可能就 2 个
MCP · exa                    4 个   但占了 9,408 字符
MCP · context7               2 个   其中一个说明 2,802 字符
```

## 两种用法

### 一、直接说话

模型会调这个插件自带的 `tool_keeper` 工具替你改。

| 你说 | 会发生什么 |
|---|---|
| 列出所有工具 | 按来源分组，带字符数和 token 数 |
| exa 只留网页搜索 | `exa` 那台只保留一个，其余消失 |
| 把 lexiang 整个关掉 | `lexiang` 的 7 个一起消失 |
| 关掉 create_dataset | 只关这一个 |
| context7 那个说明太啰嗦了，改成「把包名解析成库 ID」 | 改这个工具的说明 |
| include_selectors 那个参数说明也砍掉 | 改某个参数的说明 |
| 恢复某个工具的原始说明 | 撤销改写，变回服务器原样 |
| 全部关掉，别管工具了 | 总开关，插件完全停止干预 |
| 恢复出厂 | 清空所有规则 |

**改说明这件事真的有用**，举个例子：`context7` 有个工具叫 `resolve-library-id`，
原始说明 2,802 字符，改了之后 75 字符：

> 把包名或产品名解析成 Context7 的库 ID（/org/project）。
> 调用 query-docs 前必须先调它，除非用户已直接给出库 ID。

同样的意思，一句话说完。

### 二、点界面

打开 **设置 → Tool Keeper**。

| 位置 | 有什么 |
|---|---|
| 顶部 | 搜索框、全部折叠、刷新、**导出**、**导入** |
| 摘要 | 当前屏幕上有多少个工具 |
| 分组 | 内置工具、MCP · 各服务器，各是一张卡片，点标题折叠 |
| 每一行 | 图标、工具名、右边的开关 |
| 点工具名 | 展开编辑区：**左边是服务器原文，右边是你的改写**，两栏一样高 |
| 底部 | 恢复出厂 |

几个细节：

- **导出**会把配置下载成一个 `tool-keeper-config-<时间戳>.json` 文件。导出的是**磁盘上的当前配置**——如果改了还没重启，导出的也是还没生效的这份，文件和页面说的始终是同一件事。
- **导入**选一个之前导出的 JSON 文件，**整份替换**现有配置。导入前会自动把现在的配置备份成 `tool-keeper.json.bak-<时间戳>`；导入的内容有问题会被拒绝，配置不会被写坏。

几个细节：

- **标着「受保护」的工具没有开关**。画一个永远点不动的开关是骗人。
- **开关显示的状态是真的**。你在配置文件里写了「这台服务器只留两个」，被排除的在这里就显示关闭，不会骗你说还开着。
- **点关闭状态的开关是「打开」**，不是再关一次。
- **改完没重启时，顶部会有一条常驻提示**。为什么会有它，见下面「改完要重启」。

---

## 改完要重启

这是目前最大的不方便，得说清楚。

工具是在**注册那一刻**被拦下来的。已经注册进去的，改配置不会自动更新。

设置页那条「改了还没重启」的提示就是为这个准备的——它比的是**磁盘上的配置**和**内存里正在用的配置**，
不一样就报警。

---

## 也可以直接改文件

配置文件在 `~/.dsh/tool-keeper.json`，第一次运行自动生成一份空的。

```jsonc
{
  "enabled": true,                          // 总开关。false = 插件完全不干预

  "servers": {
    // 只留列出的这几个，其余消失
    "tinyfish": { "keep": ["search", "fetch_content"] },

    // 整台服务器关掉
    "lexiang": { "enabled": false }
  },

  "tools": {
    // 单独关一个。（受保护的工具写了会被拒绝，并告诉你原因）
    "mcp__exa__agent_run": "drop"
  },

  "rewrite": {
    // 只改工具说明，写法很省事
    "mcp__tinyfish__search": "搜索网页与外部知识。",

    // 同时改工具说明和参数说明
    "mcp__tinyfish__fetch_content": {
      "description": "读取网页正文，支持一次 10 个 URL。",
      "properties": {
        "include_selectors": "CSS 选择器，只提取匹配的元素。"
      }
    }
  }
}
```

### 冲突时听谁的

最具体的赢：

```
受保护  >  单工具规则  >  服务器白名单  >  服务器总开关
```

比如你把整台 `tinyfish` 关了，但又单独给 `search` 写了 `"keep"`——那 `search` 会留着，因为它更具体。

设置页显示的开关状态就是按这条链算出来的，不是页面自己猜的。

### 有几个工具关不掉

下面这些是保命的，任何配置都关不掉。关掉它们你的会话会直接卡死。

```
read  write  edit  glob  grep  pwsh
present  todo_write  ask_user_question  tool_keeper  skill
```

硬写进配置不会生效，而且会告诉你怎么回事——不会静默忽略。

---

## 只改文字，不碰结构

这一点值得单独说，因为它决定了这插件安不安全。

工具的定义里除了说明，还有一堆**真正决定怎么调用**的东西：参数类型、哪些必填、可选值范围、默认值。

**这个插件一个都不动。**

理由很直接：

- 改结构改错了 → 模型按错误的格式调用，工具直接报错，功能彻底坏
- 改文字改错了 → 最多是说明写得不准，工具照样能用

风险完全不对等，所以只做低风险的那一半。

---

## 效果有个真实的记录

有一次验证时，把 tinyfish 从 43 个工具收敛到 2 个，同时把这几个的说明改短：

| 项目 | 改之前 | 改之后 |
|---|---|---|
| 工具总数 | 101 | 60 |
| tinyfish | 43 个 | 2 个 |
| `fetch_content` 的说明 | 2,166 字符 | 36 字符 |
| `include_selectors` 参数说明 | 1,080 字符 | 19 字符 |
| `exclude_selectors` 参数说明 | 497 字符 | 22 字符 |
| 参数结构本身 | 8,443 字符 | **一点没动** |

省下的 token 是顺手的结果。**真正的收益是：你的模型面前不再摆着 43 个你不需要的工具，
以及它读到的话终于由你来说。**

出厂状态是 0——装完不省任何东西，因为还没开始挑。

## 出问题的时候不会把你锁死

| 情况 | 结果 |
|---|---|
| 配置文件写坏了 | 照常启动，全部工具放行，日志报错 |
| 插件自己出 bug | 那个工具原样放行，不卡住别的工具注册 |
| 补丁装不上 | 明确告诉你「没装上」，不假装在工作 |
| 卸载插件 | 一切回到服务器原样 |
| 重启 DSH | 正常生效（同类插件有过重启后失效的毛病，见 DESIGN 第六节） |

## 开发者速览

```bash
npm install    # 只有测试需要（react / react-dom 用来离线渲染页面）
npm test       # 161 条测试
```

`node_modules` 里只有测试用的 react，插件运行时不需要——页面用的 react 由 DSH 自己提供。

技术栈一句话：宿主半边拦截 DSH 的工具注册入口，浏览器半边是设置页，两者通过一个本地 HTTP 接口通信。
