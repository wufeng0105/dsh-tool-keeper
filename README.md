# Tool Keeper

**AI 每回答你一次，都要把手上所有工具的说明书重读一遍——包括你从来用不到的那些。这个插件让你把用不到的收起来，把留下的说明书改成你自己的话。**

---

## 先说清楚这是什么问题

你大概用过会联网、会查资料的 AI 助手。它之所以能搜网页、能读文件，是因为手边放着一堆叫「工具」的东西——搜网页是一个工具，读一个网址是另一个工具，查某个编程库的文档又是另一个。

每个工具都配着一份**说明书**，告诉 AI：我是干嘛的、什么时候该用我、参数怎么填。

这里有个容易被忽略的地方：

> **AI 每回答你一句话，都要把所有工具的说明书从头读一遍。**

不是读一次就记住。AI 没有记忆，每一轮都是把「之前的对话 + 全部工具的说明书 + 你的新问题」重新收进去读一遍。

所以工具越多、说明书越长，每轮要读的东西就越多。

---

## 麻烦在哪

**一、装一个服务，带来十几个工具，你只用得上两三个**

比如你装了一个搜网页的服务，它一口气给了 14 个工具。你常用的就两个：搜索、读网页。剩下十二个是「建数据集」「给钱包充值」「取消某个任务」这类，一年也用不上一次。

可它们照样躺在那里，说明书照样每轮被读一遍。

**二、说明书不是你写的，而且你改不了**

说明书是服务商写的，写的是它想让你看到的话。比如有这么一段：

> "You MUST call this function before 'Query Documentation' tool to obtain a valid
> Context7-compatible library ID UNLESS the user explicitly provides a library ID
> in the format '/org/project'..."

两百多个字符，全是大写命令句，一直在跟你的 AI 说「你必须先调用我」。

**AI 读到的就是这些话。而你一个字都改不了。**

**三、工具一多，AI 会挑错**

几十个工具摆在一起、名字还都很像的时候，AI 是有可能拿错工具的。两个工具都是「搜网页」，它挑哪个？说明书越啰嗦，越容易被带偏。

---

## 这个插件做两件事

**一、把用不上的工具收起来**

不是界面上藏起来。是真的不发给 AI——它从工具清单里消失，AI 根本不知道有这个东西。

**二、把说明书改成你自己的话**

服务商那段两百字的命令句，你可以换成一句大白话。

> 第二件事是这个插件真正特别的地方。DSH 自带的隐藏功能只能把工具拿掉，
> **改不了工具说的话**。为了拿到「能改」这个能力，这个插件绕了不少路
> （想了解可以看 [docs/DESIGN.md](./docs/DESIGN.md) 第一节）。

---

## 装上之后

**什么都不做也是对的。出厂状态不管任何工具**——工具数量、说明书内容，跟没装这个插件完全一样。

为什么这样设计？因为「哪个该关、哪句该改」只有你知道。一个管理工具如果一装上就替你决定关掉什么，那是替你砍功能。

### 先看一眼现在是什么样

跟 AI 说一句：

> 列出所有工具

它会按来源分组报给你，每个工具带占用字符数。比如：

```
内置工具                    49 个
MCP · tinyfish              43 个   ← 你常用的可能就 2 个
MCP · exa                    4 个   但占了 9,408 字符
MCP · context7               2 个   其中一个说明 2,802 字符
```

## 两种用法

### 一、直接说话

AI 会调这个插件自带的一个工具替你改。

| 你说 | 会发生什么 |
|---|---|
| 列出所有工具 | 按来源分组列出，每个带占用字符数，受保护的会标出来 |
| exa 只留网页搜索 | `exa` 那台只保留一个，其余消失 |
| 把 lexiang 整个关掉 | `lexiang` 的工具全部消失 |
| 关掉 create_dataset | 只关这一个 |
| context7 那个说明太啰嗦了，改成「把包名解析成库 ID」 | 改这个工具的说明 |
| include_selectors 那个参数说明也砍掉 | 改某个参数的说明 |
| 恢复某个工具的原始说明 | 撤销改写，变回服务商原样 |
| 全部关掉，别管工具了 | 总开关，插件完全停止干预 |
| 恢复出厂 | 清空所有规则 |

**改说明书这件事真的有用**，举个例子：`context7` 有个工具叫 `resolve-library-id`，
原始说明约 2,000 字符（一大段英文命令句），改了之后一句话：

> 把包名或产品名解析成 Context7 的库 ID（/org/project）。
> 调用 query-docs 前必须先调它，除非用户已直接给出库 ID。每问题最多调 3 次。

同样的意思，一句话说完。

### 二、点界面

打开 **设置 → 工具管理**。

| 位置 | 有什么 |
|---|---|
| 顶部 | 搜索框、折叠、刷新、**导出**、**导入** |
| 摘要 | 当前屏幕上有多少个工具 |
| 分组 | 内置工具、MCP · 各服务器，每个来源一个盒子包住整组，点标题折叠 |
| 每一行 | 图标、工具名、右边的开关 |
| 点工具名 | 展开编辑区：**左边是服务商的原文，右边是你的改写**，两栏一样高 |
| 底部 | 恢复出厂 |

几个细节：

- **导出**会把配置下载成一个 `tool-keeper-config-<时间戳>.json` 文件。导出的是磁盘上的当前配置——如果改了还没重启，导出的也是还没生效的这份，文件和页面说的始终是同一件事。
- **导入**选一个之前导出的 JSON 文件，整份替换现有配置。导入前会自动把现在的配置备份成 `tool-keeper.json.bak-<时间戳>`；导入的内容有问题会被拒绝，配置不会被写坏。文件不要超过 256KB。
- **标着「受保护」的工具没有开关**。画一个永远点不动的开关是骗人。
- **开关显示的状态是真的**。你在配置文件里写了「这台服务器只留两个」，被排除的在这里就显示关闭，不会骗你说还开着。
- **点关闭状态的开关是「打开」**，不是再关一次。
- **改完没重启时，顶部会有一条常驻提示**。为什么会有它，见下面「改完要重启」。

---

## 改完要重启

这是目前最大的不方便，得说清楚。

工具是在**注册那一刻**被拦下来的。已经注册进去的，改配置不会自动更新。

设置页那条「改了还没重启」的提示就是为这个准备的——它比的是**磁盘上的配置**和**内存里正在用的配置**，不一样就报警。

---

## 也可以直接改文件

配置文件在 `~/.dsh/tool-keeper.json`，第一次运行自动生成一份空的。

```jsonc
{
  "enabled": true,                          // 总开关。false = 插件完全不干预

  "servers": {
    // 只留列出的这几个，其余消失
    "tinyfish": { "keep": ["search", "fetch_content"] },

    // 整台服务器关掉
    "lexiang": { "enabled": false }
  },

  "tools": {
    // 单独关一个。（受保护的工具写了会被拒绝，并告诉你原因）
    "mcp__exa__agent_run": "drop"
  },

  "rewrite": {
    // 只改工具说明，写法很省事
    "mcp__tinyfish__search": "搜索网页与外部知识。",

    // 同时改工具说明和参数说明
    "mcp__tinyfish__fetch_content": {
      "description": "读取网页正文，支持一次 10 个 URL。",
      "properties": {
        "include_selectors": "CSS 选择器，只提取匹配的元素。"
      }
    }
  }
}
```

### 冲突时听谁的

最具体的赢：

```
受保护  >  单工具规则  >  服务器白名单  >  服务器总开关
```

比如你把整台 `tinyfish` 关了，但又单独给 `search` 写了 `"keep"`——那 `search` 会留着，因为它更具体。

设置页显示的开关状态就是按这条链算出来的，不是页面自己猜的。

### 有几个工具关不掉

下面这些是保命的，任何配置都关不掉。关掉它们你的会话会直接卡死。

```
read  write  edit  glob  grep  pwsh
present  todo_write  ask_user_question  tool_keeper  skill
```

硬写进配置不会生效，而且会告诉你怎么回事——不会静默忽略。

---

## 只改文字，不碰结构

这一点值得单独说，因为它决定了这插件安不安全。

工具的定义里除了说明，还有一堆**真正决定怎么调用**的东西：参数类型、哪些必填、可选值范围、默认值。

**这个插件一个都不动。**

理由很直接：

- 改结构改错了 → AI 按错误的格式调用，工具直接报错，功能彻底坏
- 改文字改错了 → 最多是说明写得不准，工具照样能用

风险完全不对等，所以只做低风险的那一半。

---

## 实际效果

本机当前的真实配置：tinyfish 从 43 个工具收到 2 个，5 个工具的说明书改写成一句话。
每轮请求要读的工具清单从约 35,600 tokens 降到约 12,500，省下的是那些你根本不会用的管理工具——
而留下的每个工具，说明书里写的都是你自己挑的话。

出厂状态是 0——装完什么都不省，因为还没开始挑。挑多少、改多少，全看你自己。

---

## 出问题的时候不会把你锁死

| 情况 | 结果 |
|---|---|
| 配置文件写坏了 | 照常启动，全部工具放行，日志报错 |
| 插件自己出 bug | 那个工具原样放行，不卡住别的工具注册 |
| 补丁装不上 | 明确告诉你「没装上」，不假装在工作 |
| 卸载插件 | 一切回到服务器原样 |
| 重启 DSH | 正常生效（同类插件有过重启后失效的毛病，见 DESIGN 第六节） |

## 开发者速览

```bash
npm install    # 只有测试需要（react / react-dom 用来离线渲染页面）
npm test       # 174 条测试
```

`node_modules` 里只有测试用的 react，插件运行时不需要——页面用的 react 由 DSH 自己提供。

技术栈一句话：宿主半边拦截 DSH 的工具注册入口，浏览器半边是设置页，两者通过一个本地 HTTP 接口通信。
