# 为什么这样实现

改机制之前先读这个文件。它记录的是**现行设计的依据**和**已证明行不通的路线**——
不知道这些，很容易把行不通的做法再造一遍。

用法见 [README](../README.md)。

---

## 一、要解决的问题与核心机制

配一个 MCP 服务器，它默认给你十几个工具，常用的两个，剩下的用不上；更要紧的是
**工具说明你改不了**——那是厂商写的，常带着「你必须先调用我」这类指令，跟你的真实需求打架。

所以这个插件要拿到两件东西：

1. 能挑（用不上的彻底不发给模型）
2. **能改**（说明文字由用户决定）

第 2 件是整篇设计的起因。省 token 是副产品：如果只为省 token，`restrict()` 就够了，
不必冒险拦截注册入口。

### 为什么改写必须发生在「注册」这一步

模型看到的工具说明从哪里读出来？三条证据（源码，L3）：

- MCP 工具和内置工具走**同一个注册入口** `ctx.tools.register(definition)`
  （`dsh-mcp-client/src/tools.ts`）。
- `description` 在**构造 definition 时**就已写进去，不是每次读取时取
  （`dsh-mcp-client/src/tools.ts` 的 `createMcpToolDefinition`）。
- 模型看到的 schema 是 `projectToolSchema()` 从注册的 definition 投影出来的
  （`dsh-tools/src/schema.ts`）。

所以：模型能看到的文字 = 注册那一刻存进 definition 的字段。
`restrict()` 只改变「哪些 definition 可见」，**不改 definition 内部的字段**。
结论：改写只能发生在注册期，论证闭合。

这也顺带解释了验收方法：`Tool.listTools` 返回的 `description` 就是模型看到的那份。

### 为什么不走另外两条路

- **「`restrict()` 管准入 + 另一个机制管改写」**：另一个机制照样得在注册期改
  definition，一件事做两遍，两套状态要同步，没有收益。
- **「等模型来读的时候再改」**：读取发生在 `dsh-tools` 包内部，拦截它要改宿主代码；
  且每个请求都要改一遍，成本比注册期改一次高得多。

## 二、只改文字，不碰结构

改的只有两处：工具的 `description`，和参数里的 `properties.<名字>.description`。

**不碰**：`type`、`required`、`enum`、有哪些参数、默认值。

理由是风险不对等：结构改错 → 工具直接报错，功能彻底坏掉；文字改错 → 最多是
说明写得不准，工具照样能用。只做风险低的那一半。

### 规则冲突时听谁的

服务器总开关是「整台取消注册」的一层覆盖，必须压过一切逐条规则，否则
「关 = 一个不剩」就是空话。最具体者胜只在逐条规则之间成立：

```
受保护  >  服务器总开关  >  单工具规则  >  服务器白名单
```

`rules.js` 的 `decide()` 是这条链的唯一实现，设置页显示的开关状态也取它的结果
（`effective`），不由页面另行推断。保存时归一化成单一结果再落盘，
因此界面开关是二态（开/关），不是三态。

两条边界：

- 「未知服务器」守卫只作用于服务器级规则本身：服务器不在已知集合里时跳过
  总开关与白名单判定，但**显式点名的单工具规则照常执行**——配置可能来自
  另一台机器，宁可放过服务器级推断，不放过显式意图。
- 闸门方向：白名单（`keep` 数组）与服务器总开关一样是**闸门**，在单工具规则之前判定。
  给不在白名单里的工具写单工具 `"keep"`，捞不回来——想留它，把 leaf 加进白名单。

## 三、配置为什么单独放一个文件

配置在 `~/.dsh/tool-keeper.json`，不写进 profile 的 `cordis.patch.yml`。

界面会频繁写这个文件，而 `cordis.patch.yml` 是用户的主配置，混着别人的行和注释，
程序化改写它有把用户东西冲掉的风险。分开写，坏了也只坏自己这一个文件。

---

## 四、界面为什么是设置页里的一页

注册一个 `settings.section` 槽位（`{id, order?, label?}`）就够了。

不走侧边栏面板那条路，因为那需要跟 `sidebar.panellist` 和 `main` 联动，
还要协调 dispatch，复杂度不成比例。

### 一个必须记住的坑

挂 HTTP 接口用的是 `ctx.inject(['webServer'], cb)` 这种**运行期注入**，
**不能把 `webServer` 写进 `inject` 数组**。

原因：headless 环境下没有这个服务。写进 `inject`，插件会一直等一个永远不会出现的服务，
永远 pending，宿主把它当成 web 启动失败。

---

## 五、为什么还要给模型一个工具

`tool_keeper`。设置页给人用，这个工具给模型用，两者写同一份配置、走同一套判定逻辑。
理由很简单：为了关掉一个工具，不值得专门去点界面，说一句话就行。

## 六、已证明行不通的路线

这些路线的教训是现行设计的直接依据，别再造一遍。

| 路线 | 行不通的原因 |
|---|---|
| `restrict()` + `tools/change` 事件同步（上一代方案 toolgate） | `restrict()` 读的是服务自己的 ctx（`scopeOf(this.ctx)`），作用域挂错位置就**静默不生效**；插件必须挂成 agent 作用域的子插件，「配置在哪、作用域在哪、UI 怎么连」互相牵扯；且同样改不了说明 |
| 加载时算一次黑名单（同类实现 tool-mask） | MCP 服务器是**异步连接**的，插件先加载时工具清单还是空的，黑名单算出来是空的，又没有重试机制——**冷启动必然失效**，而这恰恰是最常见的启动方式 |

注册期拦截从结构上同时避开两者：每个工具自己的注册调用里判定，作用域天然正确，
不存在「算早了」的窗口。

### 出厂基线为什么是全空

前两版基线都错：关掉 6 个「低频」内置工具是砍功能；只对 tinyfish 保留 2 个
仍然在替用户做决定——用户可能根本没用 tinyfish。

现行基线**全空**：装完跟没装完全一样。判断标准：管理工具的出厂状态不应该管理
任何东西，它该做的是把全部工具摆出来让人看见——看到是透明，关掉是决策，
前者默认给，后者等用户说。

## 七、可靠性与已知风险

五条可靠性约束，代码里所有「绝不阻断注册」「失败要可见」的注释都指到这里：

1. **冷启动即生效** —— 补丁装在 `apply` 期间，早于任何 MCP 连接（tool-mask 裁在这里，见前表）。
2. **绝不中断注册链** —— 任何本插件自身的错误都必须被吞掉并记为诊断，不能让一个工具因为插件的 bug 而注册失败。
3. **失败必须可见** —— 补丁装不上时报 `patched: false` 并在界面告警，不静默失效。
4. **配置损坏不锁死** —— 解析失败按全放行运行。
5. **总开关只关过滤，不关管理入口** —— 模型工具与设置页 API 仍然注册，否则用户失去恢复路径。逃生门不能只有门没有把手。

### 已知风险与退路

| 风险 | 症状 | 怎么发现 | 退路 |
|---|---|---|---|
| 宿主改了 `register` 的签名 | 加载就抛错，或静默不生效 | 启动时断言 `typeof register === 'function'`；装完查工具数 | 退回 `restrict()`，只隐藏不改写 |
| 服务被冻结（frozen/sealed） | `Reflect.set` 抛错 | 捕获后置 `patched: false` 并在界面告警 | 同上 |
| 内部调用绕过替换（直接 `this.register`） | 改写不生效但没有任何报错 | 装完查 `Tool.listTools` 里的 description | 同上 |
| Cordis 的代理让覆写失效 | 同上 | 同上 | 同上 |

**统一兜底**：总开关 `enabled: false`，插件完全停止干预。
