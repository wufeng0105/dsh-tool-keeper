# 为什么这样实现

改机制之前先读这个文件。它记录当前设计的依据，以及必须遵守的约束。用法见 [README](../README.md)。

一句话主线：**插件要保证「模型读到的」等于「它实际能做的」。工具和说明页是同一件事的两面，所以都要能在发出去之前改；改的只有文字，失败时一定放行。**

---

## 一、目标：说明与能力一致

模型每轮都会读到手上所有工具的说明书。这是它认识自己能力的方式——读本身不是成本，**读到的内容不成立才是**。

不成立有两种形态，插件各管一种：

**该消失的没消失。** 一个用不上的工具留在清单里，模型每次选择都要先排除它一遍。更常见的是：你关掉了四十个工具里的三十八个，工具确实没了，**但那页说明还在讲它们**。模型照着说明去找一个不存在的入口，找不到就换参数再试、或者绕远路、或者告诉你它做不到。

**该改的没改。** 说明书是厂商写的，写的时候假设它的全部工具都在，口吻也是写给所有用户看的（「你必须先调用我」「不要用别的搜索工具」）。这些对你不成立。

所以这个插件管的不是「少发几个字节」，而是**模型拿到的那份自我描述，与它真实的能力边界是否重合**。

这条目标决定了后面所有取舍：

- 为什么关服务器时说明页必须跟着消失——只藏一半，正是上面第一种形态。
- 为什么只改文字不改结构——结构决定能不能调用，改错直接坏；文字决定怎么理解，改错只是说得不准。
- 为什么 `status` 不吐原文——一次查询就把每台服务器的整页说明倒进对话，等于让模型重读它刚被要求别再读的东西。

---

## 二、为什么拦在注册期和组装期

目标是「发出去之前改」，那就得找到**发出去的那一刻**。模型看到的东西有两个来源，各有一个这样的时刻。

### 工具：只能在注册期改

模型读到的工具说明从哪来？三条源码证据（L3）：

- MCP 工具与内置工具走同一个注册入口 `ctx.tools.register(definition)`（`dsh-mcp-client/src/tools.ts`）。
- `description` 在构造 definition 时写入，不是每次读取时取（同文件 `createMcpToolDefinition`）。
- 模型看到的 schema 由 `projectToolSchema()` 从注册的 definition 投影（`dsh-tools/src/schema.ts`）。

所以模型能看到的文字 = 注册那一刻存进 definition 的字段；`restrict()` 只改变「哪些 definition 可见」，不改字段内容。**改写只能发生在注册期**，验收也因此能机判：`Tool.listTools` 返回的 `description` 就是模型看到的那份。

不走另外两条路：`restrict()` 管准入、另有机制管改写，等于一件事做两遍、两套状态要同步；等模型来读时再改，读取发生在 `dsh-tools` 内部，拦截要动宿主代码，且每个请求都要改一遍。

**时序约束**：判定必须在每个工具自己的注册调用里发生，不能「插件加载时算一次黑名单」。MCP 服务器异步连接，插件先加载时清单是空的，算出来就是空名单，冷启动必然失效——而冷启动最常见。

### 说明页：只能在组装期改

每台 MCP 服务器在系统提示词里占两处：**说明段** `mcp:<server>`，和**名单段** `mcp-resource-servers` 里它的名字。宿主组装系统提示词时提供官方 waterfall `system-prompt/assemble`，返回的 presentation 即最终结果（见 [HOST-CONTRACT](./HOST-CONTRACT.md)）。移除、改写、捕获原文都在这一次里完成，同一套 fail-open、同一个诊断出口。

### 两处为什么合成一套开关

这是第一节那条目标最直接的推论：一台服务器在提示词里占两处，**只藏工具、留着整页说明，正是「说明与能力不一致」**。所以没有「显示说明页」这个独立开关——那个组合本身就是缺陷状态，给它一个开关等于把缺陷制度化。

一个开关管两半：关 = 工具、说明页、名单名字一起消失；开 = 一起回来。

### 几个由此定下的做法

**为什么代码分成两个文件**：两个时机、两套失败模式。硬塞进一个文件只会让两边的 fail-open 互相纠缠。两条都读同一份启动时规则、都是重启生效，用户只需记一个心智模型。

**为什么改写是整段替换，而不是只换正文**：段正文自带 `### MCP server: <名>` 标题行（`dsh-mcp-client/src/connection.ts:316-317`），渲染只取 text、name 不参与。加一层「保护标题」的魔法会让左边原文与右边改写对不上，也更难判真假；直接整段替换，用户看得见自己换掉了什么。

**为什么不插入段**：`mcp:<server>` 段由服务器插件装配时注册（`server-context.ts:33-38`），连不上时正文为 `''`（`connection.ts:316-317`）——「没有说明」不等于「没有段」。真去插入只会发生在「这台服务器不在本会话作用域里」，等于把文本注入到不存在的服务器上。所以：有段就替换，没段就不动，并报「本次未生效」。

**为什么界面只在有运行时事实时才说「已隐藏 / 已生效」**：`removed` / `rewritten` 是最近一次组装真的做了什么。配置说了算、运行时说了不算的两处（未连接、完整提示词预设），说成「已隐藏」就是冒充——而「让模型以为某事成立」正是本插件要消除的那类问题，自己不能制造。

## 三、只改文字，不碰结构

改的只有三处：工具的 `description`、参数里的 `properties.<名字>.description`、服务器说明段的整段正文。

**不碰**：`type`、`required`、`enum`、有哪些参数、默认值。

这条界线正好把「说得对不对」和「调不调得通」分开：前者是本插件要修的目标，后者不是。结构改错 → 工具直接报错，功能彻底坏；文字改错 → 最多说明不准，工具照样能用。只做低风险的一半。

### 规则冲突时听谁的

```
受保护  >  服务器开关  >  单工具规则
```

服务器开关是「整台取消注册」的物理闸，压过一切逐条规则，否则「关 = 一个不剩」就是空话；最具体者胜只在逐条规则之间成立。`rules.js` 的 `decide()` 是这条链的唯一实现，设置页显示的开关状态取它的结果（`effective`），不由页面另行推断——界面开关因此是二态（开/关），不是三态。

两条边界：

- **判定不猜宿主**。工具归属哪台服务器只从工具名 `mcp__<server>__<leaf>` 解析；不读宿主配置、不问「现在有哪些服务器」。用户显式写下的规则就是意图，服务器没连上时规则自然惰性。
- **单工具规则是唯一的选择层**。没明确 `drop` 的默认 `keep`；新工具默认可见。服务器名写错或被移除时，判定不了「改名」还是「没连上」，统一降为诊断警告，规则保留，连上后自动恢复。

### 插件级启停不在本插件

停用整个插件是 DSH 插件页的职责。本插件不维护 `enabled` 之类的全局开关：关掉插件 = 本文件根本不执行，一切原样，不需要第二道总闸。

---

## 四、配置为什么单独放一个文件

配置在 `~/.dsh/tool-keeper.json`，不写进 profile 的 `cordis.patch.yml`。

界面会频繁写这个文件，而 `cordis.patch.yml` 是用户的主配置，混着别人的行和注释，程序化改写它有冲掉用户内容的风险。分开写，坏了也只坏自己这一个文件。

读写集中在 `config.js`：读解析、写前校验、原子写、备份各只有一份，宿主半、设置页 API、模型工具三条入口共用。写前校验与运行时判定共用 `rules.js` 的 `normalizeConfig()`，所以「界面能存下」与「引擎认」是同一套口径。

---

## 五、界面为什么是设置页里的一页

注册一个 `settings.section` 槽位（`{id, order?, label?}`）就够。不走侧边栏面板，因为那要与 `sidebar.panellist` 和 `main` 联动、协调 dispatch，复杂度不成比例。

### 一个必须记住的坑

挂 HTTP 接口用 `ctx.inject(['webServer'], cb)` 这种**运行期注入**，**不能把 `webServer` 写进 `inject` 数组**。headless 环境下没有这个服务，写进 `inject` 会让插件永远 pending，宿主判定 web 启动失败。

### 界面必须与引擎一致

界面是这个插件唯一能撒谎的地方，所以它的每一处显示都要能对上引擎的事实：

- 页面上的数量必须等于模型实际所见，不能「界面说藏了 N 个、实际一个没藏」。
- 写回必须保留未提交的字段：`state.rules.servers` 返回**完整条目**（`enabled` 与 `rewrite` 都在），否则界面整块提交会抹掉另一类配置。
- 控件不撒谎：整台服务器停用时该行开关置灰；其余情况下点了就真写（重启后生效）。

页面不显示任何时候的「占用」或「节省」数字——本插件的目标是说明与能力一致，不是体量；显示一个体量数字会把注意力引到错误的判据上。

---

## 六、为什么还要给模型一个工具

`tool_keeper`：设置页给人用，这个工具给模型用，两者写同一份配置、走同一套判定。为了关掉一个工具去点界面不值得，说一句话就行。

它的 `server` 动作同时管开关与说明页改写（`enabled` / `text` 二选一或同时给）。`status` 刻意**不吐原文**：一次 status 就把每台服务器的整页原文倒进对话，等于让模型重读一遍它刚被要求别再读的东西——原文只给设置页。

`list` 也不报每个工具的体量。理由相同：体量不是本插件要优化或报告的东西，报出来只会让模型和用户都去追一个与目标无关的数字。

---

## 七、可靠性与已知风险

五条约束，代码里所有「绝不阻断注册」「失败要可见」的注释都指到这里：

1. **冷启动即生效** —— 补丁在 `apply` 期间安装，早于任何 MCP 连接。
2. **绝不中断链路** —— 本插件自身的错误必须被吞掉并记为诊断：不能因插件的 bug 让工具注册失败，也不能弄坏系统提示词（waterfall 内出错时原样放行上游结果）。
3. **失败必须可见** —— 补丁装不上报 `patched: false` 并在界面告警；说明页监听器装不上报诊断。
4. **配置损坏不锁死** —— 解析失败按全放行运行。
5. **管理入口始终可用** —— 模型工具与设置页 API 不受过滤影响，用户随时能改回来。

### 已知风险与退路

| 风险 | 症状 | 怎么发现 | 退路 |
|---|---|---|---|
| 宿主改了 `register` 的签名 | 加载抛错，或静默不生效 | 启动时断言 `typeof register === 'function'`；装完查工具数 | 退回 `restrict()`，只隐藏不改写 |
| 服务被冻结（frozen/sealed） | `Reflect.set` 抛错 | 捕获后置 `patched: false` 并在界面告警 | 同上 |
| 内部调用绕过替换（直接 `this.register`） | 改写不生效但无报错 | 装完查 `Tool.listTools` 里的 description | 同上 |
| Cordis 代理让覆写失效 | 同上 | 同上 | 同上 |
| 宿主改了说明段名字或名单段文案 | 说明页半边静默失效 | 诊断「本次组装未见其说明段」/「名单段格式与预期不符」；界面不显示「已隐藏」 | fail-open：说明页原样，工具半边不受影响 |
| 完整提示词预设会话 | 说明页过滤与改写被宿主恢复覆盖 | 本插件检测不到（宿主不给标志） | 如实诊断并记入 KNOWN-ISSUES，不冒充 |

**统一兜底**：在 DSH 插件页停用插件，或在宿主里卸载——插件代码不再执行，一切原样。
