# 已知缺陷

**缺陷的唯一真相源。** 修好一条就删一条，不要别处另开一份。按影响排序。

每条回答三件事：什么情况下会出错、错在哪、为什么还不修。

---

## 一、双重加载时还原不干净

`installPatch()` 的 `restore()` 没有栈语义。

同一插件被两条 patch 行加载、或热重载时会包装两层。卸载时 A 的 restore 把 `register` 设回原始，B 的 restore 又设回 A 的包装，**残留一层**。如果别的插件在本插件之后也包装了 `register`，本插件的 restore 还会覆盖对方的补丁。

**触发条件**：同一插件被两条 patch 行加载，或热重载。日常使用碰不到。要修得改成带栈的补丁协议。

---

## 二、完整提示词预设下说明页过滤与改写都不生效，且检测不到

会话选用「完整提示词」类预设（dsh-persona `config.complete:true`）时，宿主在 waterfall **之后**无条件恢复 complete 段（`dsh-system-prompt/src/index.ts:693`），本插件对 sections 的过滤与改写被覆盖。

更麻烦的是**检测不到**：waterfall 里的段只有 name/text/interpolate，complete 标志被剥掉（同文件 667-672）；而 `deployment:persona-prefix` 段构造器恒注册（463-468），scoped 同名段又只在 complete 时出现——任何「数 persona-prefix 段」的启发式都会误报。

**当前行为**：不造假检测。组装里未见停用服务器的说明段时，诊断报「未连接，或该会话使用完整提示词预设——后者说明页过滤不生效」；配了改写却没见到段时，诊断报「改写本次未生效」。界面组头只在运行时事实（removed）成立时才说「说明页已一并隐藏」，面板只在 rewritten 含该服务器时才说「上次组装已生效」。工具半边不受此边界影响。

`instructions.js` 从不读 `section.complete`，所以「已生效」这句是推断出来的，不是验证出来的。这是 `UNVERIFIABLE`，不冒充已解决。

---

## 三、drop 写错是 fail-open

选择层只有逐条 `drop`，没有 fail-closed 的兜底：

- `tools.<名>` 写错（typo）或工具改名 → 规则匹配不到任何工具，那个工具会**按默认值重新出现**在模型的可选范围里（它又多了一个要排除的选项，但不影响可用性）。
- 一台服务器可能有几百条 drop，工具改名/下线后会留下失效条目，长期存在。

**防线**：诊断会聚合报出「N 条工具规则指向不存在的工具」，不会静默；按诊断删掉失效条目即可。

---

## 四、停用服务器的资源仍可读

服务器开关隐藏的是工具与说明页。`read_mcp_resource` 等内置资源工具背后的 provider 仍注册着停用服务器的资源（`dsh-mcp-client/src/server-context.ts:29-31`），模型若主动点名仍读得到。

**为什么不动**：资源读取是模型主动点名才发生的，不是每轮自动读到的自我描述——它不参与「模型以为自己能做什么」的判断，与本插件要修的那类失准无关。要堵得另包资源服务，超出「一个开关管两半」的范围。

---

## 五、参数改写没有独立开关

只要配了 `rewrite.<工具>.properties` 就生效。一个手滑写进去的参数改写会立刻起作用，而它改的是模型理解参数含义的依据。

---

## 六、恢复出厂没有二次确认

点一下就把全部规则清空。后端会留备份（`tool-keeper.json.bak-<时间戳>`），但页面没有提示备份在哪，也没有撤销按钮。

---

## 七、磁盘上遗留的空串改写会让所有写入口 400

`rewrite.<工具> = ""` 会被拒绝并报问题（空白说明会让模型拿到一个没有说明的工具）。但配置里若**已经**留着这样的条目，`config.js` 的写前校验会拒绝每一次写入：

```
磁盘含 rewrite.mcp__x__y=""  →  改任何工具都是 400
```

麻烦在于**界面上看不到那个键**：空串条目已被 `normalizeConfig` 丢弃，页面既不显示也点不到。

**逃生口**：`op=reset` 或 `op=set {"rewrite":{}}`。两者都需要手改或调 API，用户不会自己想到。

**为什么不自动清理**：自动删掉磁盘上的键属于替用户改数据，与本插件「不替用户做决定」的立场冲突。宁可让它报错并点名，也不静默清理。

---

## 八、导出与导入会静默丢数据

- **导出**：配置读不出来时用 `createBaselineConfig()` 顶替，返回体没有任何标记。用户以为导出了自己的配置，实际是空基线；再导回去就把规则清了。
- **导入**：只搬 `servers` / `tools` / `rewrite` 三个字段，旧字段（`enabled`、`servers.*.keep`）被无声删除，返回仍是 `ok: true`。

同一批字段在 `op=set` 里出现会 400 拒绝，在 `op=import` 里被静默丢弃——两条路的严格程度不一致。

---

## 九、`config.js` 的写盘降级是静默的

`writeConfig` 用「写临时文件 + rename」保证原子性。Windows 上目标被占用时 `renameSync` 会抛 `EPERM/EEXIST/EACCES`，此时退化为直接 `writeFileSync(path, …)`：非原子，中途崩溃会留下半截配置，**且没有任何日志或诊断**。

**为什么不动**：退化成直接写本身是合理的——不写就等于这次修改全丢。缺的只是一条日志，属于可观测性问题，不是数据正确性问题。

---

## 十、空白「不落盘」契约没有强制

`rules.js` 的注释说「空串/纯空白 = 未配置，调用方负责不把它落盘」，但 `api.js` 的 `op=set` 是整块写回。实测 `{servers:{s:{rewrite:"   "}}}` 能落盘成一条永远不生效的死键。

---

## 十一、`servers.<名>.keep` 被忽略时没有量化提示

`servers.<名>.keep` 不是合法字段（白名单功能不存在，隐藏工具请用 `tools.<完整名> = "drop"`）。`rules.js` 遇到它会报一句改写建议，但没说明**因此这批原本被藏起来的工具现在全部可见**。用户看到一句技术性报错，不知道自己刚刚多了几十个工具。

---

## 十二、preflight 有两项长期 UNVERIFIABLE

稳态输出 **7 PASS / 0 FAIL / 2 UNVERIFIABLE**。那两项只能在真机上判，判法与结论见 [TESTING](./TESTING.md) 的验收表：

- **slot 注册形态**：已真机确认 occupants 里有 `active: true`，页面可见；同宿主已上架插件用逐字相同写法。
- **完整插件集共存**：日常 profile 正常加载、无 entry 失败；一次性 profile 的完整流程未跑，不冒充通过。

---

## 十三、磁盘配置根为 `null` 时设置页静默

`readConfig` 对 `null` 返回 `raw: null, error: undefined`，`normalizeConfig(null)` 返回空问题列表，于是 `op=state` 报 `problems: []`、`stale: null`——页面显示成一份正常的空配置。

但写入口（`readConfigOrBaseline`）已经把 `null` 认定为坏配置并拒绝。**同一个事实两个判据**：页面说没事，写操作会 400。

`42` / `true` / `"abc"` / `[]` 这几种根都正常报出问题，只有 `null` 漏网，因为它同时是「文件不存在」的表示。

**为什么暂不动**：改它要区分「文件不存在」与「文件内容就是 null」，而 `readConfig` 目前用同一个值表示两件事。得先让读路径把二者分开，属于接口改动，不是一行的事。

---

## 十四、`export` 丢掉了坏配置的原文

`op=export` 用 `readConfig(configPath).raw ?? createBaselineConfig()`，把 `readConfig` 返回的 `text`（磁盘原文）丢掉了。注释写的是「坏配置也要能带出去修」，实际做不到：

- 半截 JSON → 导出的是空基线，坏原文没了
- 根为 `42` / `[]` → 导出原值，但 `import` 会以 `EBADARG` 拒收，导不回去

**为什么暂不动**：正确的做法是导出时带上原文或明确标记「这是坏配置」，这会改 `export` 的返回结构，界面与测试都要跟着动。

## 不值得修的

| 项 | 为什么不动 |
|---|---|
| `splitMcpName` 允许空 leaf | leaf 现在只用于分组显示，不参与判定 |
| `reset` 的备份文件名可预测（`.bak-<时间戳>`） | 同源 + 本地操作，最坏只是同毫秒两个备份互相覆盖 |
| 同源校验信任客户端 `Host` 头 | 浏览器无法伪造 `Host`，浏览器侧不可利用 |
| `ctx.effect` 没传 label | 只影响调试可读性 |
| `package.json` 没有 `author` 字段 | 私有项目 |
| `ctx.provide('tool_keeper')` 与 `state.source` 本仓库无消费者 | 前者是跨插件的服务契约，后者是 API 线格式。「本仓库没人用」不等于「契约允许删」——试过删除，18 条测试立刻变红 |
| `state.source` 字段界面不读 | 页面判断「服务器已停用」用的是 `rules.disabledServers`，不是 `role.source`。与上一条同一判断：可能是给别的消费者用的线格式，删了要改测试断言。真要删应连同 `sourceOf()` 一起，先确认没有跨插件消费方 |
| `ToolGroup` 与 `nextServersAfterRewrite` 各写一遍「两个字段都空才删整条」 | 浏览器半不能用 ESM import，这段重复拆不掉。两处已互指注释，改一处必须同时改另一处 |
| `instructions.js` 用字符串锚点 `as the server argument: ` 解析宿主名单段 | waterfall 只给 `{name, text}`，没有结构化替代。宿主改一个字就静默失效（有诊断兜底）。这是必要的脆弱，不是设计失误 |
| `host-snapshot.json` 只记 `tools` 服务的 5 个方法，rc.3 实有 11 个 | 快照的作用是「所依赖的方法还在吗」，不是「宿主方法全集」。`recheck` 报 0 CHANGED 不代表宿主没变化。扩到全集不产生收益，只增加维护面 |
| `package-lock.json` 版本号仍停在旧值 | 不参与发布与安装，`package.json` 为准 |
