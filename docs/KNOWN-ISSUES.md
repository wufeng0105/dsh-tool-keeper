# 已知缺陷

**这个文件是缺陷的唯一真相源。** 修好一条就来删一条，不要在别处另开一份。

按影响排序。前面几条会让人依据错误信息做决定，属于应该尽快修的。

---

## 一、服务器名的解析只认一种写法

`readKnownServers()` 在 `index.js` 里，用手写正则扫 `cordis.patch.yml` 找 `mcp-manager.servers`
下面有哪些服务器名。

它只认一种格式：4 个空格内的固定缩进、名字不带引号、不带点、行尾无注释。

下面这些**完全合法的 YAML 写法，它全部读不出来**：

```yaml
servers:
  "quoted-name":        # 引号包裹 → 读不出
  my.remote:            # 名字带点 → 读不出
      deep-indent:      # 4 空格缩进一层 → 读不出
  plain: # 行尾注释      # 行尾有注释 → 读不出
  { inline: ..., }      # 流式对象 → 读不出
```

**后果**：读不出的那台服务器，针对它的规则会**静默失效**（`decide()` 会把它当
「未知服务器」直接放行）。而诊断反而会误报「server not found」——它明明就写在文件里。

这是本项目里最接近「静默失效的过滤器比没有过滤器更坏」的一条。

**修法**：改用真正的 YAML 解析库，或把数据源换成 mcp-manager 的 Config
（`cordis_inspect_query` 的 Config provider 是权威源）。

## 二、两类配置错误没有任何提示

用户写了规则，但那条规则永远不会生效，而且没有任何地方告诉他：

- 给受保护工具配了改写：`decide()` 直接返回 keep，改写永不执行，无提示
- 给已被服务器规则丢弃的工具配了改写：工具先被 drop，改写根本没机会执行，无提示

应该报出「该工具受保护，改写不会生效」「该工具已被服务器规则关闭，改写无意义」。

---

## 三、双重加载时还原不干净

`installPatch()` 的 `restore()` 没有栈语义。

同一插件被两条 patch 行加载、或者热重载时，会包装两层。卸载时 A 的 restore 把
`register` 设回原始，B 的 restore 又把它设回 A 的包装，**结果残留一层**。
如果别的插件在本插件之后也包装了 `register`，本插件的 restore 还会直接把对方的补丁覆盖掉。

**触发条件**：同一插件被两条 patch 行加载，或热重载。日常使用碰不到。
真要修得改成带栈的补丁协议。

---

## 四、state 返回的死字段

`api.js` 的 `state` 返回的字段里，`enabled`、`chars`、`descChars` 页面零引用
（`disabledServers` 与 `servers` 已被服务器总开关用上，不再是死字段）。

`chars` 和 `descChars` 自 0.3.6 删掉字符数显示后彻底没人用，可以从 `state` 里删掉，
留着只会让后来者以为某处还在用。

---

## 五、导入超大文件时报错不友好

导入没有大小限制提示。客户端 `file.text()` 不限量，服务端 `readJson` 有 256KB 上限，
超限时内部异常 `request body too large` 原样抛给用户——没有告诉他限制是多少。

README 的导入说明里已补了一句「文件不要超过 256KB」，更彻底的修法是服务端对超限
返回 `EBADARG` + 人话。

## 六、参数改写没有独立开关

只要配了 `rewrite.<工具>.properties` 就生效。一个手滑写进去的参数改写会立刻起作用，
而它改的是模型理解参数含义的依据。

## 七、恢复出厂没有二次确认

点一下就把全部规则清空。后端会留一个备份（`tool-keeper.json.bak-<时间戳>`），
但页面上没有任何提示说备份在哪，也没有撤销按钮。用户点错了只能自己去目录里翻。

---

## 八、preflight 有两项长期 UNVERIFIABLE

稳态输出是 **7 PASS / 0 FAIL / 2 UNVERIFIABLE**。那不是「快通了」，是这两项本来就只能在真机上判。

### ① slot 注册形态

preflight 会标记 `slots.inject` 回调里出现 `slots.register` 的写法。

**本项目已判定为合法**，两条依据：

1. 真机验证过：重启后 `Slots.listSubTree('settings.section')` 的 occupants 里有
   `{ id: "tool-keeper", order: 50, active: true }`，页面可见。
2. 同宿主已上架的 `dsh-enhance` 的浏览器半用的是**逐字相同**的写法。

preflight 那条检查给的补法就是「人工打开设置页确认」，已照做。

### ② 完整插件集共存

只能在设备齐全的真机上验证：把插件装进一个复刻目标 bundle 组合的**一次性 profile**，
启动看是否出现 `1 entry did not activate`。

**当前状态**：本机日常 profile 装了它，重启后正常加载、没有 entry 失败。
但这不等于「复刻环境验证过」——一次性 profile 的完整流程还没跑。不冒充通过。

## 不值得修的

下面这些评估过，决定不动。记在这里免得以后有人重新纠结一遍。

| 项 | 为什么不动 |
|---|---|
| `splitMcpName` 允许空 leaf | 白名单不允许空字符串，实际影响为零 |
| `reset` 的备份文件名可预测（`.bak-<时间戳>`） | 同源 + 本地操作，最坏结果只是同毫秒的两个备份互相覆盖 |
| 同源校验信任客户端 `Host` 头 | 浏览器无法伪造 `Host`，浏览器侧不可利用。改成固定白名单属加固，非阻塞 |
| `ctx.effect` 没传 label | 只影响调试时可读性 |
| `package.json` 没有 `author` 字段 | 私有项目，同作者其他插件也没写 |
