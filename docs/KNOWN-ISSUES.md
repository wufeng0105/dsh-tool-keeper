# 已知缺陷

**这个文件是缺陷的唯一真相源。** 修好一条就来删一条，不要在别处另开一份。

按影响排序。前面几条会让人依据错误信息做决定，属于应该尽快修的。

---

## 一、服务器名的解析只认一种写法

`readKnownServers()` 在 `index.js` 里，用手写正则扫 `cordis.patch.yml` 找 `mcp-manager.servers`
下面有哪些服务器名。

它只认一种格式：4 个空格内的固定缩进、名字不带引号、不带点、行尾无注释。

下面这些**完全合法的 YAML 写法，它全部读不出来**：

```yaml
servers:
  "quoted-name":        # 引号包裹 → 读不出
  my.remote:            # 名字带点 → 读不出
      deep-indent:      # 4 空格缩进一层 → 读不出
  plain: # 行尾注释      # 行尾有注释 → 读不出
  { inline: ..., }      # 流式对象 → 读不出
```

**后果**：读不出的那台服务器，针对它的规则会**静默失效**（`decide()` 会把它当「未知服务器」
直接放行）。而诊断反而会误报「server not found」——它明明就写在文件里。

这是本项目里最接近「静默失效的过滤器比没有过滤器更坏」的一条。

**修法**：改用真正的 YAML 解析库，或把数据源换成 mcp-manager 的 Config
（`cordis_inspect_query` 的 Config provider 是权威源）。

## 二、两类配置错误没有任何提示

用户写了规则，但那条规则永远不会生效，而且没有任何地方告诉他。

| 情况 | 现在的行为 | 应该有 |
|---|---|---|
| 给受保护工具配了改写 | `decide()` 直接返回 keep，改写永不执行，无提示 | 报「该工具受保护，改写不会生效」 |
| 给已被服务器规则丢弃的工具配了改写 | 工具先被 drop，改写根本没机会执行，无提示 | 报「该工具已被服务器规则关闭，改写无意义」 |

> **已修（0.3.8）**：原先还有第三条——`tool.js` 写配置完全不校验。
> 现在走同一个 `saveConfig`，写前用 `normalizeConfig` 校验，坏配置拒绝落盘并抛 `EINVALID`；
> 危险 server 名（`__proto__` 等）在入口直接挡住。
>
> 同一轮也修了一条审计发现的相关缺陷：**参数改写全部未命中时诊断被吞掉**。
> 原来的守卫是 `if (verdict.definition !== definition)`，只在 definition 真被改过时才记录
> `missingParams`；而「rewrite 只配了 properties、参数名全都不存在」时 definition 原样返回，
> 于是诊断静默丢失。现在改为按 `missingParams.length > 0` 记录。

## 三、双重加载时还原不干净

`installPatch()` 的 `restore()` 没有栈语义。

同一插件被两条 patch 行加载、或者热重载时，会包装两层。
卸载时 A 的 restore 把 `register` 设回原始，B 的 restore 又把它设回 A 的包装，
**结果残留一层**。

更糟的情况：如果别的插件在本插件之后也包装了 `register`，本插件的 restore
会直接把对方的补丁覆盖掉。

**触发条件**：同一插件被两条 patch 行加载，或热重载。日常使用碰不到。
真要修得改成带栈的补丁协议。

## 四、设置页里有一半字段是死的

`api.js` 的 `state` 返回了一堆字段，页面没有用到：

| 字段 | 状态 |
|---|---|
| `enabled` | 页面零引用。总开关在界面上看不见 |
| `rules.servers` | 零引用。服务器白名单内容不可见，只能看到行上「服务器规则关闭」几个字 |
| `rules.disabledServers` | 零引用 |
| `descChars` | 零引用 |

> **`chars` 和 `descChars` 现在彻底没人用了**：0.3.6 删掉了字符数与 token 数的显示
> （用户指出那两个数字没用，而且因为取的是原文长度，改了说明之后反而越改越不准）。
> 这两个字段可以从 `state` 里删掉，留着只会让后来者以为某处还在用。

## 五、参数改写没有独立开关

设计阶段写过「参数级改写默认关闭，需要显式开启」，交付时**没做这个开关**：
只要配了 `rewrite.<工具>.properties` 就生效。

实现比设计简单，但这意味着一个手滑写进去的参数改写会立刻起作用，
而它改的是模型理解参数含义的依据。

---

## 六、恢复出厂没有二次确认

点一下就把全部规则清空。

后端会留一个备份（`tool-keeper.json.bak-<时间戳>`），但**页面上没有任何提示说备份在哪**，
也没有撤销按钮。用户点错了只能自己去目录里翻。

## 七、preflight 有两项长期 UNVERIFIABLE

稳态输出是 **7 PASS / 0 FAIL / 2 UNVERIFIABLE**。那不是「快通了」，是这两项本来就只能在真机上判。

### ① slot 注册形态

preflight 会标记 `slots.inject` 回调里出现 `slots.register` 的写法。
理由是 2026-11-10 出过一次「设置页看不到」的事故，是同类形态。

**本项目已判定为合法**，两条依据：

1. 真机验证过：重启后 `Slots.listSubTree('settings.section')` 的 occupants 里有
   `{ id: "tool-keeper", order: 50, active: true }`，页面可见。
2. 同宿主已上架的 `dsh-enhance` 用的是**逐字相同**的写法（`ui/client.js:926-927`）。

preflight 那条检查给的补法就是「人工打开设置页确认」，已照做。

### ② 完整插件集共存

只能在设备齐全的真机上验证：把插件装进一个复刻目标 bundle 组合的**一次性 profile**，
启动看是否出现 `1 entry did not activate`。

**当前状态**：本机日常 profile 装了它，重启后正常加载、没有 entry 失败。
但这不等于「复刻环境验证过」——一次性 profile 的完整流程还没跑。不冒充通过。

## 不值得修的

下面这些评估过，决定不动。记在这里免得以后有人重新纠结一遍。

| 项 | 为什么不动 |
|---|---|
| `splitMcpName` 允许空 leaf | 白名单不允许空字符串，实际影响为零 |
| `reset` 的备份文件名可预测（`.bak-<时间戳>`） | 同源 + 本地操作，最坏结果只是同毫秒的两个备份互相覆盖 |
| 同源校验信任客户端 `Host` 头 | 浏览器无法伪造 `Host`，浏览器侧不可利用。改成固定白名单属加固，非阻塞 |
| `ctx.effect` 没传 label | 只影响调试时可读性 |
| `package.json` 没有 `author` 字段 | 私有项目，同作者其他插件也没写 |
